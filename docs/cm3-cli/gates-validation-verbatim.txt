G0 — Safety/correctness: zero wrong-target writes, unauthorized SPI writes, corrupted verified data, uncorrected memory-test errors, kernel panics/oops, filesystem errors, unexplained resets or lost mandatory interfaces. No safety/security regression is tradable for speed. Any such fault stops promotion and triggers diagnosis.

G1 — Boot/install: both fresh installs provision distinct nonempty machine identity and distinct SSH host keys, no reusable permanent default credential, and reach serial login plus authenticated SSH. All 20 cold and 20 warm attempts succeed for each claimed boot medium. First-boot growth affects only the selected OS partition and no other disk. Expansion and shutdown/reboot behavior must be tested, not inferred from unit enablement.

G2 — Debian/security: APT update and the prescribed upgrade complete without signature errors, mixed-release dependency hacks or dpkg audit errors; a standard package install/configure/remove cycle and post-update reboot succeed. Security repository delivery, vendor update ownership and matching ABI/modules are verified. Rejected unsigned/tampered metadata must remain rejected in an isolated negative-test fixture. No production trust bypass is permitted. Two installs expose only documented listening services and have secure authorized access.

G3 — Thermals/power: within published electrical/temperature ratings, all required sensors and cooling-control paths function; kernel thermal protection stays enabled. A proposed test abort margin is 5 C below the lowest relevant critical trip, or a stricter vendor limit. Establish sensor interpretation and an independent observer/watchdog before load. If the margin would overlap ordinary passive throttling, redesign the safe test envelope rather than changing trips. Stop for sensor loss, thermal-control failure, undervoltage indications, PSU faults or expanding error counts. Never heat deliberately to critical shutdown or disable cooling/protection to prove it works. Record normal throttling; it is not automatically a failure if the supported design throttles safely. Any candidate worsening temperatures, throttling duty cycle or energy must have an explicit reviewed trade-off within ratings.

G4 — Performance non-regression: after B0 exists, compute baseline run-level coefficient of variation (CV) per workload. Initial tolerance is max(5%, 2*CV), capped at 10%; CV above 5% makes the workload inconclusive until controls or sample size improve, not permission to relax beyond 10%. Apply to median throughput (lower bound), and run-level p95 latency and power/energy (upper bound). Report uncertainty; an interval spanning a disallowed regression is inconclusive, not PASS. For a tuning benefit claim require a paired 95% interval excluding zero and median benefit exceeding max(3%, baseline CV), on a named primary metric, with G0-G3 and all secondary non-regression gates intact. Primary metric and trade-off budget are preregistered; no post-hoc best-score selection.

G5 — Responsiveness/liveness: authenticated SSH probe has a proposed 5-second timeout and the local small CLI probe a 1-second timeout under the bounded standard loads; zero timeouts and no service starvation in the mandatory suite. Also enforce G4 on run-level p95 and report p99/worst probe time. Owner may replace these provisional ceilings with workload requirements before tests, not after results. Memory pressure beyond the supported envelope is a separate controlled failure test, not evidence that ordinary-load stalls are acceptable.

G6 — Sustained performance: after warm-up, compare final 15-minute throughput with the initial 15-minute measured window and with B0's corresponding windows. Proposed allowable further decline is 5%; if exceeded, extend the run, inspect throttling/ambient/storage state and report as unresolved rather than calling the early peak sustained. No progressive memory growth, new error count, unbounded swap/I/O stall or failed probe during the final 8-hour soak.

G7 — Coverage: every mandatory/core row in hardware-matrix.tsv must be PASS on the claimed configuration before a stable release. Conditional rows need PASS to claim support; absent hardware is NOT PRESENT only after physical inventory. With missing equipment, status is UNTESTED, not NOT PRESENT or PASS. A core FAIL/UNTESTED is a no-go for stable qualification; the consolidator may propose a clearly labelled development artifact only after separate authorization. An optional limitation may be declared without pretending to provide full hardware coverage. UNSUPPORTED requires evidence of an incompatible route/driver/API, not just a failed first try.
